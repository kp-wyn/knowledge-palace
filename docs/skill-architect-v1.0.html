一、什么是技能架构师

技能架构师（Skill Architect）：在 AI 时代，把真实业务与知识场景中的问题，通过技能架构设计、流水线编排和系统集成，转化为可复用、可运行、可进化的技能系统的人。
技能架构师 = 场景洞察 × 技能设计 × 流水线编排 × 系统沉淀

三重责任：

① 对真实问题负责——不是坐在办公室猜需求，而是进现场看真实流程；
② 对技能系统落地负责——不是写一份技能说明书，而是做出被真实工作流程跑通过的技能；
③ 对知识资产沉淀负责——不是做一次丢一次，而是把个案抽象成可复用的技能模块。

为什么是现在？

三个趋势汇合：AI 能力爆炸但落地困难；技能（Skill）正在成为新基建；一人公司（OPC）崛起。大多数人会用 AI 工具，但没有人系统地"设计技能架构"——就像人人都会用电脑，但不是人人都会设计企业 IT 系统。这个缺口，就是技能架构师的位置。

散装 Agent 的三个典型病症

过去半年，大量一人公司老板装了 20-30 个 AI 工具、配了一堆工作流，看起来热火朝天，一到商业交付就掉链子。问题出在三处：

病症表现
① 互相不通写文案的 Agent 不知道做图的产出了什么，回邮件的不知道客户谈到哪一步——信息全靠老板人工搬运，一人公司变成"一人给 AI 打工"
② 没有骨头AI 写出来的是网上扒的通用套路，不是老板自己的行业判断和方法论——客户一眼看出是 AI 模板
③ 无法沉淀这个月踩的坑下个月还踩，每次交付从零开始，经验只存在老板脑子里，AI 调不动
你买了一堆发动机、方向盘、轮胎堆在车库——那不叫车，开不上路。你有的是工具，不是系统。

为什么是知识宫殿法催生了这个职业？

知识宫殿法（KP-4+1）是一套个人与组织知识操作系统：以宫殿为隐喻，把碎片化知识按地基层（采集）→结构层（建模）→加工层（提取激活）→调控层（复盘迭代）四层组织起来，由人机协同层贯穿全程，让人在 AI 时代把知识真正变成可复用的能力。提出者：王亚宁（kp-wyn）；对应著作《知识宫殿法：KP-4+1 个人与组织知识操作系统》及《知识宫殿：AI时代如何重建你的判断力、体系感与知识价值》（两本著作权登记申请中）。

为什么是它，而不是别的笔记法或知识管理工具，催生出"技能架构师"这个角色？三个原因：

知识宫殿法的设计为什么必然长出技能架构师
宪法第五条·蒸馏优先明确规定"宫殿是工作台，不是仓库"——信息管理只作辅助，核心产出必须是方法论蒸馏成技能。既然产出是技能，就得有人负责设计和编排技能
宪法第三条·kp- 技能命名成熟方法论必须封装为 kp- 前缀的可挂载技能，统一索引、随时调用。这本身就是"技能架构"工作——不是随便写个提示词，而是按规范建技能
加工层：从知识到技能加工层核心任务就是"提取→激活→迁移→蒸馏技能"。知识卡是最小可调用单元，技能是更大的可调用单元——从卡片到技能的跃迁，需要专门的架构设计

换句话说：大多数知识管理方法止步于"存好、连好"，知识宫殿法从第一天起就要求"蒸馏成可调用技能"。既然方法本身以技能为核心产出，那个负责设计技能、编排流水线、沉淀资产的角色——技能架构师——就是这套体系的自然产物。目前知识宫殿法已挂载 130+ 个 kp- 技能，这些技能本身就是技能架构师工作方法的实践样本。

二、和其他角色的区别

不是什么

  • 不是外包开发——外包交付完就走，不对业务结果负责
  • 不是产品经理——PM 画原型，技能架构师让技能真跑起来
  • 不是培训讲师——讲师讲完就完，技能架构师沉淀可调用系统
  • 不是数据分析师——分析师出报告，技能架构师把报告变成流水线
  • 不是 AI 提示词工程师——提示词是单轮对话，技能架构师做的是端到端系统

是什么

  • 进真实场景，画场景地图
  • 把模糊问题翻译成可拆解约束
  • 设计单个技能的触发条件、输入输出、SOP、边界
  • 把多个技能编排成端到端工作流
  • 接入真实工具链和知识库
  • 把每次交付沉淀成可复用技能资产

参考 Palantir 的 FDE（Forward Deployed Engineer，前置部署工程师）——工程师直接进客户现场，把问题跑成可运行系统。技能架构师是 FDE 在知识与业务领域的对应角色：

FDE（Palantir）技能架构师（一人公司/知识场景）
客户现场你的真实工作场景
工程实现技能设计与流水线编排
系统集成接入你的飞书/微信/Excel/知识库
产品沉淀技能模块库持续复利

本质是同一件事：把真实问题跑成可运行的系统，而不是交付一堆零散功能。不同的是，FDE 服务大客户，技能架构师服务一人公司与知识工作者——规模更小、速度更快，但对"经验结构化"的要求一点不低。

门槛澄清：技能架构师不要求会写代码。它要求的是——能把自己做事的步骤写清楚（"我做这件事先看什么、再判断什么、最后产出什么"），让 AI 照着做。写不出来的人，才需要技能架构师帮他把脑子里的东西倒出来。

三、能力栈 L1-L6

L6
系统架构：技能库 + 工具链 + 知识库 + 调度器的整体设计
→ 架构图
L5
资产沉淀：把个案抽象为可复用技能模块，让知识复利
→ 技能模块库
L4
流水线编排：多技能串成端到端工作流（串联/并联/分支/反馈循环/人工节点）
→ 可运行流水线
L3
技能设计：单个技能的触发条件、输入输出、SOP、失效边界
→ SKILL.md
L2
问题翻译：把"我想要个方案"这种模糊需求，拆成可执行约束
→ 需求清单
L1
场景洞察：深入真实使用场景，听懂真实目标，画场景地图
→ 场景地图

常见风险：只会代码像外包；只会沟通像顾问；不会沉淀做一次丢一次。L3 是分水岭——能独立设计一个完整技能，才算是入门。

四、六步工作流

步骤做什么产出
① 进场景看真实使用流程，而不是听人转述需求场景地图
② 拆问题找卡点、断点、重复劳动点问题清单与约束
③ 设计技能最短路径跑通最小可用技能原型SKILL.md + 知识卡
④ 编流水线多技能串联/并联/分支，跑通端到端流程可运行工作流
⑤ 接系统嵌入真实工具链、知识库、业务流程真实上线点
⑥ 沉淀资产用反馈迭代技能，个案变通用模块技能模块入库
技能架构师的产出不是一份技能说明书，而是被真实工作流程使用过的技能系统路径。

五、三层体系

第一层：单个技能设计规范

一个技能就是一个目录，核心是一份 SKILL.md：

层级内容何时加载
元数据name + description（约 100 tokens，让调度器知道什么时候调它）始终在上下文
指令层SKILL.md 正文：SOP、规则、红线、输出格式技能被激活时
资源层references / templates / scripts / assets需要时才读

第二层：流水线编排（多技能协同）

模式说明示例
串联A 输出 → B 输入 → C 输入收集需求 → 写方案 → 做 PPT
并联多技能同时跑，结果汇总搜竞品 + 查政策 + 分析市场
条件分支根据判断走不同路径数据够 → 直接分析；不够 → 先补
反馈循环输出 → 评估 → 不合格 → 回退重跑写初稿 → 评分 → 不达标 → 重写
人工节点关键判断点暂停，等人确认再继续方案生成 → 等老板确认 → 再执行

第三层：技能系统架构

最上层是用户/业务场景；中间是调度器（Agent/OS），它决定什么时候调哪个技能；调度器下面是三件套——技能库、工具链、知识库+记忆；最底层是大模型（已经标准化，不用自己造）。技能架构师的主战场不在底层模型，而在中间这三层。

六、核心应用场景

场景技能架构师做什么
知识运用把知识宫殿从仓库变成技能工厂——存知识是为了用，用的方式是技能调用
商业经营把"老营销人的经验"变成"新人也能调用的技能"——经验不再只存在某个人脑子里
企业管理决策层/管理层/执行层三层技能系统，老板只看异常和决策点
一人公司你是调度器不是执行者——内容/营销/客服/财务/情报各由技能 Agent 负责

谁需要技能架构师？四条判断标准

如果你中了两条以上，就该认真考虑给自己配一个技能架构师（或自己上手做）：

① 每周重复性工作超过 10 小时，值得技能化；
② 脑子里有一套方法论，但每次都要从零重新输出；
③ 接商业单时，担心 AI 交付质量不稳定、会掉链子；
④ 经验只存在你脑子里，人走茶凉，没沉淀成可复用资产。

反过来，如果你只是偶尔用 AI 问个问题、写个东西——那是普通用户，不需要。

一人公司不是"一个人干一个团队的活"，那是累死。一人公司是"一个人调度一套技能系统，系统帮你干活，你只管判断和方向"。
